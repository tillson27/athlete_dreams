# Athlete Profile: Share Surface, Core Values, and URL Consistency Fixes

Date: 2026-08-25
Task slug: profile-share-and-values-fixes
Status: Complete

## 0) Summary

- **Objective:** Fix three athlete-reported defects on the public profile — the mobile share button being invisible, core values silently disappearing on save, and `?profile=` query URLs leaking into share links — and add native mobile sharing so an athlete can post their résumé card straight to social.
- **Why now:** Direct athlete feedback on the live site. All three defects sit on the growth loop: the profile is the shareable artifact, and every one of these bugs blocks or degrades a share.
- **Primary outcomes:**
  - The SHARE button is visible on mobile profiles again.
  - Sharing on mobile uses the native share sheet (image + link), plus a Copy link action.
  - Core values entered anywhere (onboarding or the manage editor) persist, render, and are deletable.
  - Profile URLs are the path form (`/athletes/<slug>`) everywhere, including share links and the generated card image.

---

## 1) Success criteria

- On a mobile viewport at both `/athletes/<slug>` and `/athletes?profile=<slug>`, the profile's sticky action bar (Back/Follow + SHARE) is visible and tappable, and the site's mobile bottom nav does not overlap it.
- Tapping SHARE on a mobile browser that supports the Web Share API opens the OS share sheet carrying the generated PNG and the profile link.
- A core value saved with a title but no "what it means to you" body survives a save/reload round-trip and renders on the public profile.
- Values chosen during onboarding appear as editable, deletable rows in the manage editor's Core Values section.
- Saving a core value in the manage editor never causes previously visible values to disappear from the public profile.
- `profileUrl('maya-okafor')` returns `athletearc.ca/athletes/maya-okafor` in every data-source mode, and the share card image renders that URL.
- Existing `?profile=` links already in circulation still resolve to the profile.

**Acceptance criteria (definition of done):**
- `npm run ci` passes from the repo root.
- A static export build (`STATIC_EXPORT=true npm run build --prefix client`) succeeds — this is the deployed build mode and is where `useSearchParams` boundary errors surface.
- `npm run test --prefix cdk` passes, including a new assertion covering the `/athletes/<slug>` CloudFront rewrite.
- No step leaves a `?profile=` or `?manage=` href generated by application code.

## 3) Background and motivation

ARC (`athletearc.ca`) is the athlete résumé product. Per root `AGENTS.md`, crowdfunding within an athlete's own network is the go-to-market motion, and per `client/AGENTS.md` the profile is story-first and minimalist. That makes the public profile the single most important shareable artifact in the product — an athlete posting their card to Instagram is the primary acquisition loop, and `AthleteProfile.tsx:568-586` explicitly frames every profile as "a recruiting billboard".

Step 5 of that task added free-text onboarding values, and Step 8 fixed a highlight date being silently discarded on save — structurally the same defect class as the core values bug here.

The three reported defects:
1. "There is no share button on the mobile version still" — plus a request for a quick way to share a profile visual by link and to social.
2. "When I edit my profile and add core values, there's nothing showing my old core values and a way to delete them. When I go to my profile view, I can't see my new core values that I've added."
3. "Athlete profile URLs ... why are they appearing in share links as `profile`? should be consistent everywhere."

## 4) Current state and gaps

### Current state

- The mobile share button exists: `client/app/(marketing)/athletes/[athleteSlug]/AthleteProfile.tsx:589-612` renders a sticky bar containing `<ShareCard resume={shareResume} compact />`.
- `client/components/site/MobileBottomNav.tsx:57-59` hides itself on profile pages with a hand-rolled regex: `/^\/athletes\/[^/]+$/.test(pathname)`.
- `client/lib/profileUrl.ts:9-15` routes real athletes through `?profile=<slug>` whenever `NEXT_PUBLIC_DATA_SOURCE !== 'mock'`, because `generateStaticParams` in `client/app/(marketing)/athletes/[athleteSlug]/page.tsx:7-9` only pre-renders the mock roster.
- `cdk/lib/web-stack.ts:71-74` already rewrites `/athletes/<slug>` and `/athletes/<slug>/manage` to `/athletes.html` at the CloudFront viewer-request stage.
- `client/app/_components/AthleteRouteFallback.tsx`, wired into both `client/app/not-found.tsx` and `client/app/(marketing)/not-found.tsx`, catches the client-side-navigation case where the Next router 404s on a slug it never pre-rendered.
- `client/app/(marketing)/athletes/AthleteDirectory.tsx:47` resolves the route from `window.location.pathname` plus params via `athleteRouteFromPath`, so both URL forms already render a profile.
- Core values are stored as `Json?` at `app/prisma/schema.prisma:233` and read defensively by `app/src/api/athletes/AthleteService.ts:363-371`.
- Onboarding writes bare value words to a separate `values: string[]` field (`client/lib/onboardingApi.ts:122`); the manage editor reads and writes only `coreValues` (`client/lib/manageApi.ts:116-122, 151`).
- `client/lib/shareImage.ts` renders the branded card to a canvas at six platform sizes. `ShareCard.tsx:130-157` offers Download plus web intents for X/Facebook/LinkedIn.
- The existing copy-link pattern lives at `client/app/(marketing)/dashboard/DashboardClient.tsx:469-473` and `client/app/register/review/PublishPanel.tsx:126-130`.

### Gaps

- **Nav collision.** The `MobileBottomNav` regex only matches the path form. In production the URL is `/athletes?profile=<slug>`, so `pathname` is `/athletes`, the guard misses, and the nav renders. Both elements are `fixed` at `z-40`; the nav is `bottom-0` while the share bar is at `bottom: env(safe-area-inset-bottom)` and the nav is later in the DOM, so the nav paints over the SHARE button. Verified against the dev server: `/athletes?profile=maya-okafor` renders the nav (1 occurrence), `/athletes/maya-okafor` does not (0 occurrences).
- **No native share.** `rg 'navigator.share|canShare'` returns nothing across the repo. The share modal has no Copy link action either. On mobile, Download-then-manually-attach is the only path.
- **Title-only core values are silently dropped.** `client/lib/manageApi.ts:291-293` filters on `value.title.trim() && value.body.trim()`. `common/src/zod/athlete.ts:69-72` backs this with `body: z.string().min(1)`. The editor presents the body input with no required marker, and unlike highlights/races/roadmap — which `throw` a visible error — core values are filtered with no feedback. Api-mode only; mock mode persists the whole edits blob to localStorage, so it does not reproduce locally.
- **Onboarding values never reach the editor.** `profileToEdits` reads `profile.coreValues` and ignores `profile.values`, so signup-era values are invisible and undeletable in the manage UI.
- **Saving one core value hides the onboarding values.** `AthleteProfile.tsx:385-411` renders `profile.coreValues` *or* falls back to `athlete.values`. The first saved core value flips the branch and the onboarding pills vanish from the public profile.
- **No CDK coverage for the rewrite.** `rg 'athletes' cdk/test/web-stack.test.ts` returns nothing, so the rewrite that the whole path-URL plan depends on is untested.

## 5) Changes and considerations

**Significant changes:**
- `athleteCoreValueSchema.body` stops being required. This is a contract change and must follow the repo's Zod-first order: `common/` → build `common` → `app/` → `client/`.
- `client/lib/profileUrl.ts` loses its runtime/static branch entirely; every generated href becomes the path form. This is a broad ripple — 14 call sites across the client.
- `MobileBottomNav` gains a dependency on search params, which in a static export needs a Suspense boundary.

**Impact and considerations:**
- `values` is load-bearing beyond display. `client/app/(marketing)/dashboard/DashboardClient.tsx:100` uses `profile.values.length > 0` as a profile-completeness checklist item, and `client/app/register/review/PublishPanel.tsx:72,86` uses it as a publish-readiness gate. **`values` must therefore never be cleared** when core values are saved — it must be kept in sync instead, or the dashboard checklist regresses and publish readiness breaks.
- Old `?profile=` links are already in circulation (they appear on the athlete's posted Instagram card). `athleteRouteFromPath` must keep reading `?profile=` and `?manage=` forever, even after generation stops.
- `ManageProfile.tsx` is also targeted by the incomplete `arc-editor` task. Different section of the file; expect and absorb concurrent edits per root `AGENTS.md`.

## 8) Proposed approach

- Route matching moves to the single shared helper. `MobileBottomNav` stops owning a private regex and calls `athleteRouteFromPath(pathname, searchParams)` — the same helper `AthleteDirectory` and `AthleteRouteFallback` already use. This is what stops the bug class recurring: there is then exactly one definition of "is this a profile URL" in the client.
- The core value contract relaxes rather than the client compensating. Making `body` tolerant at the schema is a smaller, more honest change than teaching three call sites to fake a body.
- Values bridging is read-merge plus write-sync, not a data migration. On load, core values are the union of stored `coreValues` and any `values` not already represented. On save, `values` is rewritten from the core value titles so the two stores agree and deletions stick — without ever emptying `values` and breaking the dashboard/publish gates.
- URL canonicalization is gated on evidence. The path form is only made canonical after the CloudFront rewrite is confirmed live, and a CDK test is added so it cannot silently regress.

## 9) Data model and contracts

### OpenAPI changes

This repo is Zod-first; there is no `common/openapi.yaml`. The contract lives in `common/src/zod/athlete.ts`.

`athleteCoreValueSchema` (`common/src/zod/athlete.ts:69-72`):

```ts
// before
export const athleteCoreValueSchema = z.object({
  title: z.string().min(1).max(120),
  body: z.string().min(1).max(2000),
});

// after
export const athleteCoreValueSchema = z.object({
  title: z.string().min(1).max(120),
  body: z.string().max(2000).default(''),
});
```

`.default('')` is chosen over `.optional()` deliberately: it accepts both an omitted and an empty body on input while keeping the inferred output type `body: string`, so `AthleteCoreValue` is unchanged and no downstream consumer needs a `?? ''`.

Consumers of the schema, both unchanged in shape:
- `athleteProfileSchema.coreValues` — `common/src/zod/athlete.ts:113`
- `updateAthleteProfileRequest.coreValues` — `common/src/zod/athlete.ts:188` (`.max(12)` cap retained)

### Data model changes

None. `coreValues` is already `Json?` (`app/prisma/schema.prisma:233`) and `values` is unchanged. No Prisma migration.

### Example shapes

A valid core value after this change:

```json
{ "title": "Mental health", "body": "" }
```

## 11) Edge cases and error handling

- **Core value with body but no title:** throw `'A saved core value needs a title.'` from `toStoryAndValuesPatch`, surfaced through the editor's existing save error banner. Mirrors `manageApi.ts:170-172`.
- **Core value fully blank:** dropped silently, as blank highlights are. No error — the athlete added a row and left it alone.
- **Bridged value deleted then saved:** `values` is rewritten from the surviving core value titles, so it does not resurrect on reload.
- **Value title longer than 40 chars:** `values` entries are capped at 40 by `common/src/zod/athlete.ts:112`, while core value titles allow 120. Truncate to 40 when syncing back into `values`, and cap the array at 8 per `athlete.ts:187`.
- **More than 12 merged core values:** truncate to 12 before sending; the schema enforces `.max(12)`.
- **`navigator.share` present but `canShare({files})` false:** fall back to `navigator.share({title, text, url})`.
- **`navigator.share` absent (most desktop):** hide the native button, keep platform intents and Download.
- **User dismisses the OS share sheet:** `navigator.share` rejects with `AbortError`. Swallow it — it is not a failure.
- **`navigator.clipboard` unavailable (non-secure context):** swallow and leave the URL visible to copy manually, matching `DashboardClient.tsx:471-473`.
- **Canvas is tainted:** `ShareCard.tsx:60-62` sets `crossOrigin='anonymous'`, but a non-CORS host would taint the canvas and make `toBlob` throw. Catch it and fall back to link-only sharing.
- **Legacy `?profile=` link after Step 6:** still resolves via `athleteRouteFromPath`.

## 12) Failure modes and concurrency

**Concurrency/race conditions:**
- The manage editor saves sequentially (`manageApi.ts:308-323`) and is single-owner, last-write-wins. The `values`/`coreValues` sync rides the same `patchMyProfile` call as `coreValues`, so the two fields cannot diverge across a partial failure.

**Idempotency and retries:**
- `patchMyProfile` is a PATCH with a full replacement array for `coreValues` and `values`; re-running a save is idempotent. The read-merge is also idempotent — once `values` mirrors the core value titles, the merge is a no-op.

**Failure modes:**
- If the CloudFront rewrite is not live, Step 6 must not run. Flipping `profileUrl.ts` without it would 404 every share link.
- If `npm run build --prefix common` is skipped after the schema edit, `app/` and `client/` type-check against a stale `fad-common` and the contract change appears to work while failing at runtime.
- A missing Suspense boundary around `useSearchParams` fails the static export build, not the dev server — which is why the acceptance criteria require the export build explicitly.
